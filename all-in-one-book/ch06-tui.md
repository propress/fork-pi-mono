# 第六章 pi-tui — 终端 UI 框架

前五章我们走完了 Pi 的核心主线：LLM 通信 → Agent 运行时 → CLI 与会话 → 工具与扩展。但用户看到的不是这些后端逻辑——用户看到的是终端中实时滚动的文本、彩色的代码高亮、工具执行的动画。这些视觉效果由 pi-tui 负责。

pi-tui 是一个独立的终端 UI 框架——它不依赖 Pi 的任何其他包，你可以单独用它构建终端应用。但它是 Pi 交互模式的视觉引擎。

---

## 6.1 终端渲染的根本挑战

在浏览器中渲染 UI，你有 DOM、CSS、虚拟 DOM diff。在终端中，你只有一个字符网格和一组 ANSI 转义序列。

终端 UI 的核心挑战是**闪烁**（flicker）：如果你每次更新都清屏重绘，用户会看到短暂的空白闪烁。这在快速更新时（比如 LLM 逐 token 输出）尤其明显。

pi-tui 用两个技术解决闪烁问题：

**差分渲染**（Differential Rendering）：不清屏重绘，而是找到变化的行，只更新那些行。

**同步输出**（Synchronized Output）：用 CSI 2026 转义序列把一次渲染的所有写操作包裹在原子块中。终端缓冲所有输出，直到块结束才一次性刷新到屏幕。

---

## 6.2 Component 接口

pi-tui 的核心抽象是 `Component` 接口——可能是你见过的最简洁的 UI 组件接口：

```typescript
interface Component {
  render(width: number): string[];      // 给定宽度，返回行数组
  handleInput?(data: string): void;     // 可选：处理键盘输入
  invalidate(): void;                   // 清除缓存，强制重新渲染
  wantsKeyRelease?: boolean;            // 是否接收按键释放事件
}
```

`render()` 是核心——组件接收当前视口宽度，返回一个字符串数组（每个字符串是终端中的一行）。字符串可以包含 ANSI 转义序列（颜色、粗体等），但**可见字符宽度不能超过 `width`**。

这个设计的优雅之处在于**组件不需要知道自己在屏幕上的位置**——它只关心宽度。定位、排列、差分比较都由 TUI 容器处理。

对于需要输入焦点的组件（如编辑器），有一个 `Focusable` 接口：

```typescript
interface Focusable {
  focused: boolean;  // 由 TUI 设置
}
```

焦点组件通过在渲染输出中插入一个特殊标记（`CURSOR_MARKER`）来告诉 TUI "光标应该放在这里"。TUI 解析这个标记来定位终端光标——这对输入法（IME）支持至关重要，因为 IME 候选窗口需要显示在光标位置。

## 6.3 差分渲染的三种策略

TUI 容器在每次渲染时决定使用哪种策略：

**策略一：首次渲染**。没有历史数据，直接输出所有行。不清屏——这样不会破坏终端的回滚缓冲区。

**策略二：宽度变化或视口上方有变化**。此时差分计算的成本超过重绘，直接清屏并全量渲染。

**策略三：常规更新**（最常用）。从上一次渲染的结果中找到第一个发生变化的行，把光标移动到那里，清除该行及以下的内容，只重绘变化的部分。

```
渲染前                      渲染后
┌─────────────────┐        ┌─────────────────┐
│ Line 1          │        │ Line 1          │  ← 没变，跳过
│ Line 2          │        │ Line 2          │  ← 没变，跳过
│ Line 3 (old)    │  →→→   │ Line 3 (NEW)    │  ← 变了，从这里开始重绘
│ Line 4          │        │ Line 4 (added)  │
│                 │        │ Line 5 (added)  │
└─────────────────┘        └─────────────────┘
```

所有输出都包裹在同步输出块中，终端保证原子刷新：

```
\x1b[?2026h      ← 开始同步输出（终端开始缓冲）
...渲染内容...
\x1b[?2026l      ← 结束同步输出（终端一次性刷新）
```

## 6.4 键盘输入处理

终端的键盘输入是以转义序列的形式到达的——按下方向键上，程序收到的是 `\x1b[A`。不同的终端和协议产生不同的序列。

pi-tui 统一了两种键盘协议：

- **传统终端序列**：标准的 ANSI/VT 转义码。大多数终端支持，但有局限——比如 Ctrl+Shift+P 和 Ctrl+P 产生相同的序列，无法区分。
- **Kitty 键盘协议**：现代协议，支持修饰键的精确检测、按键释放事件。需要终端支持（Kitty、WezTerm、iTerm2 等）。

pi-tui 在启动时检测终端是否支持 Kitty 协议。如果支持，启用增强模式；否则退回传统模式。对上层来说，API 是统一的：

```typescript
import { matchesKey, Key } from "@mariozechner/pi-tui";

if (matchesKey(data, Key.ctrl("c"))) process.exit(0);
if (matchesKey(data, Key.enter)) handleSubmit();
if (matchesKey(data, Key.ctrl("shift+p"))) cycleModel();  // Kitty 协议下可区分
```

## 6.5 内置组件

pi-tui 提供 12 个内置组件：

| 组件 | 作用 | 关键特性 |
|------|------|---------|
| **Text** | 单行/多行文本 | ANSI 颜色保持、自动换行 |
| **TruncatedText** | 截断文本 | 超过宽度时添加省略号 |
| **Editor** | 多行文本编辑器 | 撤销/重做、自动补全、垂直滚动、快捷键 |
| **Input** | 单行输入 | 基本编辑操作（Ctrl+A/E/W 等） |
| **Markdown** | Markdown 渲染 | 语法高亮、代码块、列表 |
| **SelectList** | 交互式选择列表 | 模糊过滤、键盘导航 |
| **SettingsList** | 设置面板 | 值循环、子菜单 |
| **Loader** | 加载动画 | 旋转器动画 |
| **CancellableLoader** | 可取消加载 | 旋转器 + AbortSignal |
| **Image** | 内联图像 | Kitty/iTerm2 图像协议 |
| **Box** | 布局容器 | 内边距、背景色 |
| **Spacer** | 垂直间距 | 空行填充 |

其中 **Editor** 是最复杂的组件——它实现了一个功能完整的文本编辑器：多行编辑、光标移动、选区、撤销/重做栈、文件路径自动补全、斜杠命令补全。Pi 的交互模式用它作为用户输入框。

**Markdown** 组件也值得一提——它把 Markdown 文本渲染为带语法高亮的终端输出。Pi 用它来渲染 LLM 的回复。

## 6.6 Overlay 系统

对于模态对话框（如模型选择器、设置面板），pi-tui 提供了 Overlay 系统：

```typescript
const handle = tui.showOverlay(component, {
  width: 60,              // 固定宽度
  maxHeight: "50%",       // 最大高度为视口的 50%
  anchor: "center",       // 屏幕居中
  margin: { top: 1 },     // 上边距
});

// 控制
handle.hide();
handle.show();
handle.focus();
```

Overlay 渲染在所有普通组件之上，支持灵活的定位方式：锚点（9 个方位）、百分比、绝对坐标。

## 6.7 小结

pi-tui 的设计哲学是**最小抽象**：

- **Component 接口**只有一个核心方法（`render(width) → string[]`），组件不需要知道布局位置。
- **差分渲染**用三种策略覆盖所有场景，结合同步输出消除闪烁。
- **键盘处理**统一了传统序列和 Kitty 协议，上层用统一 API。
- **12 个内置组件**覆盖了终端 UI 的常见需求。
